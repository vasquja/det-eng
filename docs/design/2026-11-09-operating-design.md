Companion to [`2026-11-09-design-review.md`](2026-11-09-design-review.md). Written for the owner's stated goal: one person, little direction, Claude researches, tests and writes detections on its own, coverage scales quickly, and "working" is established by CI rather than by the owner reading pull requests.

How this was produced: three agents each designed the system from one angle (adversary-proof verification, throughput, zero-touch operations), two judges scored them against the repository and the tooling (one as a sceptical detection lead, one as the owner's stand-in), and a critic looked for what all five missed. Both judges picked the verification-first design and grafted the throughput plumbing and the operational guardrails onto it; the critic added the half of a detection's life none of them covered (retiring and rewriting rules, closing defects, what coverage should count, what the real cost meter is). The plan below is that merged result, with the disagreements resolved by evidence and the unverified items listed at the end.

## 1. What the goal changes

Under this goal four things in the review change weight.

- **The human loop is not the fix; the machine is.** The review's flaw 8 (the human loop is nominal) is mostly the intended model. The question becomes how to make a green run trustworthy with nobody reading the diff, and how to stop the README promising a human review that will not happen.
- **The closed loop is the central risk.** Today a cloud rule's rule, fixture, cases, benign slices and budget are one hypothesis about the log written five times by the same author. With no human reading PRs, nothing catches what the gates miss. A free public corpus already shows the failure: `entra_app_federated_credential_backdoor.yml` misses a real federated-credential record because the real keys are lowercase (`issuer`, `subject`) and the hand-written fixture uses `Issuer`, `Subject` under a case-sensitive regex. No current gate can see this class because both sides are the agent's.
- **Throughput is bounded by the process, not the agent.** The last six waves shipped 39 TRRs in 24 days, about 11 a week, despite eight-technique PRs, a hand integration commit that renumbers defect IDs, three hand-copied path lists per workflow, four whole-corpus snapshot files, and a 92 KB ledger the agent must read every round. Remove those and parallel sessions become possible. CI is not the limit: the longest required check runs about 5.5 minutes, the kind job costs about 100 seconds fixed plus 9 seconds per Kubernetes technique, and Actions minutes are free on a public repository.
- **Every step that waits on the owner is a bottleneck.** Waiver digests, budget raises, defect-ID renumbering, the hand merge of every PR, sandbox runs, and the "Needs the maintainer" sections of recent PRs must each become a machine precondition, a scheduled job, or a rare label.

One fact constrains everything: **Claude Code cloud sessions act as the owner's account today.** `gh api user` from a session returns `vasquja`, and every merged PR is authored by that account. Every rail that depends on "a human applied this label" or "the agent cannot approve" is prose until the session's identity changes. The plan therefore starts with an identity experiment and uses one rail that binds regardless of identity (gate code overlaid from `main`).

## 3. Operating model

**Identities.** The owner's account, and an agent identity: a `det-eng-agent` machine user with a fine-grained token (contents and pull requests, write, this repository only) injected into the cloud session's network secrets for `github.com` and `api.github.com`. If a cloud session still pushes as the owner after that (unverified), builders open PRs through a small `claude-code-action` job instead. `.github/CODEOWNERS` routes every non-content path to the owner. The ruleset keeps required approvals at 0, no bypass actors, squash only, and adds code-owner review and approval of the most recent push.

**Weekly cadence.**
- Monday, after the existing 06:53 UTC re-proof crons: `harvest-evidence.yml` downloads the newest validator artifacts (apiserver telemetry, static-pod telemetry, the Linux benign capture), sanitises them, and opens one content-only evidence PR from the agent identity that auto-merges when green. It also writes the weekly digest issue.
- Monday 09:00: the planner (a Claude Code scheduled task, fresh session) refreshes the candidate records, vets up to a dozen candidates through the GO/NO-GO gate, files one issue per GO (label `go`, oracle tier in the body), and spawns N builder sessions.
- Tuesday to Saturday: each builder claims one `go` issue by self-assigning and creating branch `trr/<9000+issue>-<slug>` (ref creation is atomic, so two builders never take the same issue), builds one technique, opens a draft PR within its first hour, drives it green, marks it ready. It never adds labels and never edits gate code, budgets, slices, waivers, evidence files or external-source lists.
- Continuous: CI runs the required checks (about 6 minutes). `automerge.yml` arms native auto-merge when the PR is content-only, authored by the agent identity, not a draft, carries no `hold` label, has no CHANGES_REQUESTED review, every check on the head is green, fewer than K agent merges landed in the last 24 hours, and `main`'s last push run has no failed required check.
- Sunday: the digest issue is complete: techniques merged by provenance tier, waivers and budgets the machine accepted (with revert links), PRs waiting on a label, live-capture divergences, external-record disagreements, mutation survivors, red schedules, sessions that opened no PR, kill-switch events.
- Quarterly, and whenever a cloud fixture's field model changes: `emulate-cloud-live.yml` runs the live cloud emulations in sandbox accounts and commits the captured records.

**The owner** reads the digest, applies `hold`, `ratchet-override` or `budget-approved` where the digest asks, and approves the batched infrastructure PR. Target under one hour a week.

**Kill switch.** One repository variable, read first by the planner, every builder, the harvest, the cloud capture and the automerge rail. Revoking the agent token stops everything else.

## 4. Trust architecture: how CI establishes "working" without a reader

In the order they should land. Each names what it catches that nothing catches today.

1. **Gate code from `main`, not from the PR.** A composite action overlays `detections/*.py`, `.github/scripts/`, `research/tools/` and `detections/pipelines/*.py` from `origin/main` in every checking job and fails any PR that touches those paths unless it carries a human-only `infra` label. Catches a grader edit hidden in a large diff (wave 5 changed 80 lines of `check_provider_mappings.py` and 271 of the apiserver validator inside 124 files). Binds today, before the identity split. Half an agent-day.
2. **The gates test themselves.** `detections/tests/known_bad/` holds about 20 planted artifacts each gate must reject (a rule keyed on the emulation's names, a trivial near-miss, a fixture whose casing contradicts its rule, a budget raise citing no defect, a live script without an undo trap, a compact-JSON-only match, a null-unsafe `not`) and a pytest job runs them with the three self-tests no workflow runs today (`sigma_explain`, `check_null_safety`, `check_provider_mappings`). Fix the Linux no-op: grade vacuity for every control, and replace the no-op with a per-rule wrong-argument control for the seven rules it alone covers. Required check. 2.5 agent-days.
3. **External records the agent did not write, available today.** `splunk/attack_data` (Apache-2.0) holds 39 CloudTrail, 18 Entra, 12 Kubernetes audit, 112 auditd and 6 GCP captures. Twenty-one of this repository's cloud and Kubernetes rules have a same-technique dataset; five fire on it; two T1537 rules fire as true positives on a bucket-decommission capture; the copyfail correlation fires ten times on the real CopyFail auditd capture; one Entra rule misses the real record. `detections/external/SOURCES.json` (URL, sha256, licence, technique, log source), a fetcher with a cached fallback, and `check_external_records.py`: a same-technique dataset defaults to `expect: fire`; `quiet` and `n/a <reason>` declarations live in a CODEOWNERS-protected file, so a real-record miss is the one thing the owner looks at. Every dataset of a rule's log source is also scored as a benign slice. A passing external positive gives the rule the `third-party-sample` tier. Catches the K64/K66 class (field name, casing, nesting shared by rule and fixture). 2 agent-days; the owner accepts the licence once.
4. **Harvest CI's own captures into committed evidence.** The validators already compute the records the kernel or API server actually wrote for each emulation (`stimulus_hits` and the ledger windows); the artifacts already exist and are thrown away after 30 or 90 days. Add `--evidence-out` to the four lab validators, a sanitiser (pids, uids, temp paths, hostnames, audit IDs, emulation names to stable placeholders), and the weekly harvest PR committing `<stem>.captured.jsonl` positives and recorded benign slices with a `_harvest` block (workflow run id, query) that a lint confirms through the Actions API, plus a committer check through the commits API (login and `verification.verified`, since a git author string is forgeable). Linux and Kubernetes rules reach the `captured-lab` tier automatically. The keyring rule firing on `systemd-executor` at budget 0 in 18 consecutive runs becomes a committed recorded slice that `score_benign.py --enforce` fails instead of a warning nobody reads. Add `score_benign.py --live-grace 3` so a live hit that is not yet a committed slice still fails after three weeks. 3 agent-days.
5. **Provenance tiers read by merge policy.** An enum on sidecar `source` (`synthetic`, `reasoned-from-source`, `blind`, `third-party-sample`, `captured-lab`, `captured-live`), on fixture records and on slice fidelity, enforced by lint. `check_sufficiency.py` reports each rule's strongest passing tier; `coverage_report.py` renders `proven-live`, `proven-recorded`, `proven-synthetic`, `claimed`; a required `provenance-tier` check fails when a tier drops versus `main` and when a new rule is below its platform's policy tier (`detections/provenance_policy.json`: Linux and Kubernetes `captured-lab`, which the harvest supplies; cloud `third-party-sample` or `captured-live`, otherwise the rule merges and counts as Claimed, never Proven). Remove the word "recorded" for hand-written fixtures from `README.md`, `AGENTS.md`, the skill, `build-and-prove.md`, the cloud validator and the cloud workflow header. The GO gate's third question changes from "provable with committed fixtures" to "has an oracle at the platform's policy tier", or the planner keeps selecting cloud candidates that can only merge as Claimed. 1.5 agent-days.
6. **Mutation as a ratchet.** `check_mutants.py` builds mutants from each rule's items (delete an item, widen a value to `*`, drop a `not` block, case-fold a value, equality to `contains`), compiles each with the real backend, and marks it killed when any sidecar, captured or external case flips verdict or the benign hit count changes. At HEAD, 41 to 72 percent of simple mutants survive per platform. Gate as a ratchet against `main`'s own run (survivors per rule may not rise), plus for a new rule no surviving widen of a discriminating item; a kill by an external or captured record outranks a kill by a sidecar case the same PR adds. Not a fixed kill ratio: legitimately redundant items (`eventSource` beside `eventName`) survive delete mutants by construction. Catches over-broad items, dead items and dead filters, which one near-miss per rule cannot. 2 agent-days.
7. **Representation variants inside the oracle that exists.** `check_provider_mappings.py` gains providers keyed by log-source product rather than Kubernetes only: compact and sorted JSON text, a `json_each` multi-valued list model, case-sensitive `LIKE`, and an RE2 `regexp` function swapped into `sigma_eval.EventTable` (ten lines; `regexp` is already registered there). Every case runs under each variant; gate as no new divergence; record the 19 exploded and 2 compact losses as expected-loss entries and fix the two GCP rules in their own PRs. Write `detections/SEMANTICS.md` with the probes as golden tests and delete the "same answer any conforming backend would give" sentence from `sigma_eval.py`. 3 agent-days.
8. **Approvals as verifiable properties.** A chokepoint or presence waiver is honoured only when the rule is verifiably pure-surface, holds at least two verified negatives, has budget 0 or cites an open defect, is level medium or lower, and is its TRR's only waived rule; an expected-loss entry only when the counterfactual transform already in `check_provider_mappings.py` proves the reason; a level-high rule with a non-zero budget must cite an open defect. The owner's remaining act on these is a click on a data-only PR, not a read. 1 agent-day.
9. **Sandbox cloud capture, the only fix for the cloud loop.** A `sandbox` GitHub environment restricted to `main`, OIDC trusts into three throwaway accounts with spend alarms, `atomics/lib/live.sh` (undo stack, `trap run_undo EXIT INT TERM`, an account, tenant or project guard) sourced by the 17 live-gated scripts with a lint, a harvester that pulls CloudTrail, Azure Activity, Graph directory audits and sign-ins, and GCP logging for the run window by marker, a `fixture_diff.py` that fails a committed fixture whose field path, casing or type the capture lacks, and captured-live records landing through the evidence PR. Runs on dispatch after one supervised round, then quarterly and whenever a fixture's field model changes; eleven of the scripts tamper then restore in a real tenant, so weekly is wrong. The owner provisions the accounts once. 3 agent-days, one human day.
10. **Deferred to month 2.** Blind cases written by a bot-committed job that sees only the TRR's procedure table and the vendor field index, never the rule (a subagent inside the build session is only a prompt; nothing can tell its cases from authored ones). A schema oracle derived from botocore service models and the kind cluster's OpenAPI (shadow only, opaque string values exempt; it cannot see the Entra casing case, which lives inside a JSON string).

## 5. Throughput architecture: parallel builders with no hand integration

- **One technique per PR**, enforced: at most one new `research/trrNNNN/` directory, at most 60 changed files, every path inside that technique's namespace. No wave branches, no integration commit.
- **Identifiers without coordination.** TRR id = 9000 plus the backlog issue number (GitHub's counter is atomic; the local band is reassigned upstream anyway, so sparse IDs cost nothing); defect IDs namespaced per rule (`<stem>-<n>`, with a namespace for the eleven Linux rules that have no TRR); waivers already keyed by rule path.
- **Per-rule sidecars replace every shared registry.** `<stem>.gates.json` beside each rule (cloud: TRR, fixtures, provider, marker fields; Kubernetes: the `rec`/`win` keyword arguments as JSON with the 44 custom-helper calls kept in Python as a named registry; Linux: source, arguments, controls), `<stem>.waivers.json`, `<stem>.budget.json`, `<stem>.defects.jsonl`, `<stem>.portability.json`, loaded through a new `detections/validator_common.py` and converted from the existing tables by a one-off script. A rule in a listed folder with no gates entry fails instead of compiling as "not manifest-gated". Widen `sigma_eval._RULE_MATERIAL` and R0 for the new suffixes, or every gate refuses to import on the first sidecar.
- **Per-TRR fragments** for `research/index.json`, the `research/README.md` table and the technique's Atomic Red Team YAML (the T1098.001 YAML is shared by four TRRs and is where wave 5's interleave bug came from), rendered by a merge script with `--write/--check`, plus an ART YAML lint (declared inputs, executor present, arguments agree with the gates file).
- **Derived files leave the PR diff.** `scores.json`, `policy_coverage.json` (347 KB, changed in every Kubernetes PR), `mapping_results.json`, `COVERAGE.md` and the charts stop being committed in technique PRs; every corpus-wide check runs head-live against base-live with `main`'s own script (the pattern `sufficiency-ratchet` already uses), and a render job publishes them to a `reports` branch or a bot PR. No merge train and no strict up-to-date: a stale base costs one CI cycle because `automerge.yml` refuses to arm while `main`'s last push run is red.
- **Workflow wiring derived at run time.** Each `changes` job calls the validator's `--paths`; the cloud filter is dropped (the validator runs in one second); the 18 apiserver emulate anchors and their 18 aliases become one loop step over the gates files.
- **Emulate and validate in separate jobs** for the three kind workflows (job A builds the cluster, runs the atomics, uploads the audit log and ledger; job B on a fresh runner runs the validator with `main`'s gate code). That is what lets Kubernetes atomics be content. Linux stays one job because the validator spawns the binaries itself as root, so Linux atomics stay non-content and a Linux technique PR needs the owner's click: one or two a week, recorded as the residual.
- **Backlog as issues.** `research/tools/backlog.py` ranks candidates by ATT&CK gap (from a derived index, not the 55 MB bundle), platform balance, oracle tier and novelty, and the digest reports GO yield per platform; a candidate record may name only technique IDs present and not revoked in the index, and every prior-art citation must resolve. The 92 KB ledger shrinks to the playbook plus a rendered 5 KB summary.
- **Backpressure.** One open PR per issue; a draft red for 48 hours is closed and its issue unclaimed; builders have a wall-clock and push cap; the digest lists sessions that opened no PR.

## 6. The other half of a detection's life

The critic found that every design optimised one path, adding a technique, and left the rest human-gated. Under this goal these matter as much.

- **Retiring or rewriting a rule has no autonomous path.** Today the ratchet counts a deleted or renamed rule and any edit to an existing case as a decrease; `budgets.json` fails on a rule that no longer exists and is human-only; closing a ledger entry needs the owner at three steps; retiring one Kubernetes rule touches 15 files outside its directory. With 57 open defects each proposing a fix, the defect backlog becomes the bottleneck the build path no longer has. Fix: a `status: deprecated` plus `<stem>.retired.json` path that the ratchet treats as an allowed decrease when a defect record names it, render steps that drop the rule's budget, waiver, expected-loss and resource rows, and `ratchet-override` only when evidence is weakened with no defect citation. 1.5 agent-days.
- **Defect closure needs a machine precondition.** Closing defects moves more procedures to Proven (51 are "proven, open defect") than building techniques, `RULE_DEFECTS.md` edits auto-merge today as `.md` content, and the proving case named in each entry's "Then" is prose no tool reads. Add a `known-miss` case kind (must not fire today; the defect record names it; when the rule fires it the defect closes and the case becomes a positive), a check that every open false-negative or evasion defect has one and every closed defect's case exists and passes, and put defect records under the same protection as budgets. 1 agent-day.
- **Coverage should count something the agent did not choose.** The headline "32 of 33 techniques have a rule" counts only techniques the agent picked. Report techniques with a tier-2 proven procedure over the ATT&CK techniques tagged for the platforms in scope, and pin a prevalence source (URL and sha256) as a rank term so the backlog has an external input. 1 agent-day; the owner picks the denominator in 15 minutes.
- **The reviewer job is effectively empty.** It finishes in 35 to 71 seconds, posted one comment on 14,695 lines, can only post inline comments, cannot run `sigma_eval.py`, and the action restores `.claude/` and `CLAUDE.md` from `main` at run time but not `AGENTS.md`, which `CLAUDE.md` includes, so a PR can still instruct its reviewer. Either turn it into a check that runs the skill's skeptic prompts per changed rule with Bash and Python allowed and writes findings as an artifact the digest reports, or remove it and spend the subscription on the blind-cases job. Add a `Claude-Session:` trailer lint so every merged change links to its transcript (12 of the last 60 commits carry one).
- **Licence.** No root licence, no `license:` per rule. The external-records gate redistributes Apache-2.0 samples (attribution needed), the harvest commits captures, and upstream filing, the only external review this model will ever get, is impossible without a grant. Root `LICENSE`, `license:` per rule, a `NOTICE` for vendored samples, and a quarterly upstream batch as a planner task that the owner files. 15 minutes of decision, half an agent-day.
- **The platform ceiling.** The ledger records 41 NO-GO against 22 GO; the GO rate is about 25 percent; candidate supply across the five platforms saturates in three to five months. The candidate record carries an `oracle` field the planner must fill, the digest shows GO yield per platform, and a new oracle (a `windows-latest` runner with Sysmon or the event log, the same shape as the auditd job; capture mechanics unverified) is a scheduled infrastructure project of about four agent-days.
- **Vendor-document drift.** The TRRs carry 392 external URLs and three retrieval dates; nothing re-reads them. A `sources.json` per TRR (URL, retrieved, sha256 of the fetched text) written by the builder and re-fetched monthly, with a digest row when a hash changes. 1 agent-day.
- **The real meter is the Claude subscription.** Actions minutes are free. Four builders of 6 to 10 hours, the reviewer on every push, the planner and the blind-cases job all draw on one subscription with usage caps; a builder looping on red (20 to 30 percent of first attempts) burns that cap. Per-session wall-clock and push caps, the digest reporting pushes per merged PR, and the reviewer gated to ready-for-review only.

## 7. What the owner still does

| Duty | Why it stays human | Time |
|---|---|---|
| Approve the batched infrastructure PR (gate code, workflows, skills, `AGENTS.md`, budgets default, slices, external sources, known-bad set) | The gates are what make green trustworthy; an agent that can rewrite them can pass anything | 20 to 30 min a week |
| Apply `ratchet-override`, `budget-approved`, `hold` where the digest asks | These are the only moves that turn red green without new external evidence, so the decider must be a party that cannot benefit | 10 min a week, 2 to 4 events |
| Read the digest and veto | The one place a human sees what the machine accepted; replaces PR reading | 15 to 20 min a week |
| Provision once: the agent identity, three sandbox accounts with spend alarms and OIDC trusts, the licence decision, the coverage denominator | Credentials, money and intent | About two days once, then an hour a quarter for pin bumps |
| Upstream filing | Repository policy; the only external review | Optional, hours per batch |

The infrastructure PR is the duty the owner is least likely to do carefully, and it is where a gate weakening would slip in. The known-bad set is the backstop: a gate change that stops rejecting a planted artifact is a red required check, whatever the owner read.

## 8. Guardrails, enforced by machine

- Gate code overlaid from `main` in every checking job; a PR touching it needs the human-only `infra` label.
- Labels are human-only by check: a label counts only when the latest `labeled` timeline event's actor is a human user with write access (the events API exposes the actor; verified on PR #47); a label applied by the agent identity is ignored and reported.
- Ratchets computed by `main`'s own scripts: cases, verified negatives, exercised items, benign hits, mutation survivors, representation divergences, provenance tier, rule complexity. Escape only by `ratchet-override`, and only when the identity split exists.
- Evidence the agent is graded on is unwritable by the agent: captured files carry a `_harvest` block confirmed through the Actions API and a committer check through the commits API; external datasets are sha256-pinned under CODEOWNERS.
- Scope caps: one technique per PR, 60 files, paths inside the technique's namespace, draft never arms, a body containing "do not merge" or "WIP" never arms.
- Rate limit and off switch: at most K agent merges per 24 hours; one repository variable stops every scheduled job and the merge rail.
- Live emulation cannot leave the sandbox: `live.sh` refuses unless the caller identity matches the configured account; every tamper runs inside an undo stack with EXIT, INT and TERM traps; the 20 kubectl scripts refuse a context that does not match `^kind-` or an exported lab context; builder sessions hold no cloud credentials; the capture job's OIDC role has a spend cap that disables it.
- Budgets and corpus are human-only; a level-high rule with a non-zero budget must cite an open defect; recorded slices land only through the harvest PR.
- Supply chain: every action SHA-pinned with `dependabot.yml`; `sigma-cli` pinned to the validators' pySigma (today the lint job resolves a different major version); the reviewer and blind-cases jobs restore `.claude/`, `CLAUDE.md` and `AGENTS.md` from `main`.

## 10. Expected throughput and the ceiling

After the plan, with four builders: 8 to 12 merged techniques a week, each in its own PR at the `third-party-sample` or `captured-lab` tier, with cloud techniques lacking an external record merging as Claimed. Assumptions: one technique per session in two to four wall-clock hours (observed in waves 5 and 6 once integration and the hand merge are removed), CI iteration about six minutes, 20 to 30 percent of first attempts red and returned to the backlog, a GO rate of 25 to 35 percent so the planner vets about 40 candidates a week.

The ceiling is candidate supply and the subscription, not CI. The vet ledger shows GO rates falling as the easy adjacency is mined; past about 15 a week the planner spends more on NO-GOs than builds, and saturation across the five platforms arrives in three to five months. After that the same sessions turn to defect closure, grounding the synthetic tiers with captures, the rules-for-the-channel work, and a new oracle.

## 11. Disagreements, resolved

- **Atomics as content.** One design made them content with no guard; one relied on a tree hash, a root-owned copy and an execve watch; one allowed Kubernetes atomics only after the emulate/validate job split and kept Linux non-content. The process-tree attribution exists only in the Linux validator, the kind validators read logs from paths, and root ownership isolates nothing when both run as root. The split is the mechanism; Linux stays non-content.
- **Live cloud capture cadence.** Weekly, monthly, or quarterly after a supervised round. Eleven scripts tamper and restore in real tenants, and a fixture is a schema sample that needs re-capture only when a rule's field model changes. Quarterly plus on-change.
- **Mutation gate form.** A fixed kill ratio fails correct rules with redundant items; the ratchet plus no surviving widen of a discriminating item is the calibrated form.
- **Blind cases.** An in-session subagent is a prompt; a bot-committed file from a job that sees only the TRR is isolation. The second, once its push path is proven.
- **Derived files.** A merge train with strict up-to-date re-runs every open PR on every merge and the repo documents why strict is off. Base-versus-head checks with nothing committed, and a main-red rail.
- **Identity.** Two designs assumed sessions act as an App; sessions act as the owner today. The gate-from-main overlay is the one new rail that binds before the split; everything label-based waits for it.
