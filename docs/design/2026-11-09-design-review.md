# det-eng: design review

> **Design record, written 2026-11-09 and kept as written.** It reviews the repository
> as it was at commit `1b2cba3`. The work that follows from it is tracked in
> [`../ROADMAP.md`](../ROADMAP.md). Where this record and the roadmap disagree, the
> roadmap is current. Changes since it was written: the repository has a licence
> (`LICENSE`, `detections/sigma/LICENSE.md`), a `CODEOWNERS` file and setup guides
> ([`../setup/`](../setup/README.md)).

Reviewed at commit `1b2cba3` (2026-11-05). Ten reviewers each took one dimension and produced 65 findings with file-level evidence. The claims this document leans on were then reproduced by hand, and a second pass of 29 agents tried to refute every flaw section (one hostile fact-checker and one fairness judge per section), judged the redesign for realism, and looked for what everyone had missed. That pass refuted one example, corrected about thirty numbers and citations, re-sized the redesign, and added five flaws. This is the corrected version. The appendix says what was verified and how.

## Summary

The repository's thesis is sound and unusual: a rule is done only when a machine shows it fires on its own emulation and stays quiet on controls. For Linux auditd and the Kubernetes API server that thesis is real. The atomic runs on a real kernel or a live kind cluster, the rule is compiled by the real pySigma backend, and a record has to come from the emulation's own process tree or ledger window. The repository is also unusually candid in its inner documentation about what it has not done.

The flaws are in what surrounds that core, and most share one root: **the system validates the agent's model of the world against artifacts the same agent produced from that model, and its top-level claims describe that as proof on recorded telemetry.** Six consequences follow.

1. **Cloud rules have no external oracle, and the top-level wording says otherwise.** All 17 cloud fixture folders are hand-written JSON; no cloud sidecar case is recorded; the cloud emulation scripts never run in CI and have no capture mode. The README says CI runs rules on "recorded cloud audit logs", the agent's skill tells it to call the fixtures "recorded", and `research/COVERAGE.md` counts 25 cloud procedures among its 66 "Proven". Two TRRs and the skill's own gotcha list say the fixtures are "documentation-derived, not captured", so the repository disagrees with itself.
2. **The evaluator's semantics are accidental for the cloud rules.** Lists are flattened to Python `json.dumps` text and matched with `|contains` and `|re`. Two GCP rules lose their only attack hit when the same list is serialised without spaces. Equality is case-sensitive, `|contains` is not, and equality on a list field never matches. For Kubernetes the repository already tests two serialisations and marks the 19 rules that a store exploding arrays would silently lose; for the cloud rules there is no such check, no pipeline for any store, and the AWS rules carry 112 regexes over 500 characters.
3. **The negative evidence is thinner than its labels.** A near-miss kills one mutant class (delete this item); the repo's own ledger shows the defect classes it cannot find. The Linux no-op control can never pass by construction. Twenty-seven chokepoint waivers carry a rule digest but no approver, and were added in the PRs they excuse. The one live false-positive signal (a runner capture) has shown a budget-0 rule firing on `systemd-executor` in every run since 2026-10-16 and nothing consumed it.
4. **Prose is the data model.** Coverage is computed by regex over Markdown tables and by substring search of a rule's filename in the validators' source. Defects, waivers, budgets and the vet ledger are hand-kept; the ledger the agent must read "first, every round" grew from 7 KB to 92 KB in three weeks. The ATT&CK mapping is already stale against the repo's own statement of v20.
5. **The human loop is structurally thin and the README overstates it.** One maintainer authors every PR under one account, so no approving review can exist; a 14,695-line PR merged after 1 h 40 m; a PR whose body said "please do not merge yet" merged with a rule that fires on every apiserver restart; the only human-account review comments on the two largest PRs read in the agent's voice. The inner docs say all of this plainly; the README says "a human-approved waiver" and "a budget a human approves" without the caveat.
6. **What ships is not yet consumable through the channel the repo names.** The Azure and GCP rules declare SigmaHQ log sources but use the provider's raw field vocabulary, `UPSTREAM.md` points GCP contributions at a path that does not exist, the Atomic Red Team YAML is never executed or linted and nine tests reference an undeclared input, the rule `modified` field is missing on about half the changed rules, and the repository has no licence.

The redesign keeps the core (real oracles, the real compiler, the ratchets, the defect ledger) and changes four things, in this order: split the agent's identity from the maintainer's so the existing approval rails can work; make provenance a typed, graded field that the coverage report reads; run the cloud emulations once in sandbox accounts so every log source has at least one record the agent did not write; and extend the representation checks the repo already has to the cloud rules inside the existing evaluator. Everything else is cheaper than the first version of this review proposed.

## What the design gets right

- **Real oracles for Linux and Kubernetes.** The atomic runs on a real auditd host or a live kind cluster, a pre-emulation log is scored with `--expect-miss` as a negative control, each apiserver procedure is bound to its emulation window, and dry-run controls must stay quiet.
- **One real Sigma compiler on the evaluation path.** pySigma plus its SQLite backend is the only matcher. `rule_cases.py` carries a differential oracle (the item-by-item verdict from `sigma_explain.py` must agree with the compiled SQL on every case) and `check_null_safety.py` runs every rule under two- and three-valued logic.
- **Ratchets and an honest defect ledger.** The sufficiency ratchet fails any edit or deletion of an existing case and any rise in benign hits. `RULE_DEFECTS.md` shows 51 procedures as validated-but-defective rather than hiding them, classifies evasions as a defect kind, and its "Checks to add" section records the gate's own limits.
- **The Kubernetes portability work.** `check_provider_mappings.py` runs every Kubernetes sidecar case through AKS and GKE pipelines in compact and sorted serialisations with real GKE anchor records, and `PLATFORMS.md` marks every rule a store that explodes arrays would lose. `audit-policy-recommended.yaml` is a deployable production audit policy with per-distro steps.
- **Grounded Kubernetes research.** `research/trr9031/k8s/README.md` pins every chokepoint claim to versioned Kubernetes source, and the reviewer verified each citation. TRR9022's prior-art paragraph is accurate and specific.
- **Candour in the inner documentation.** `detections/README.md`, `detections/benign/README.md`, `COVERAGE.md`'s "Limits of this report", the skill's gotcha list and the ledger's evidence vocabulary all state the limits this review describes. The flaws below are mostly about the gap between those statements and the top-level claims, the agent's instructions, and the tooling.
- **Careful lab supply chain.** kind, kubectl and the node image are pinned by digest; dispatch inputs are regex-validated; vendored provider policies carry upstream digests and licences.
- **A selection-first gate** that records NO-GOs with reasons and has dropped weak candidates before anything was built.

## Flaws

Severity is impact on the trustworthiness, portability or usability of the rules and TRRs, or on the ability to keep producing them. Where the challenge pass disagreed with the first draft, the corrected figure is given.

### 1. The cloud proof loop is closed on the agent's own artifacts, and the top-level wording hides it (high)

**Claim.** For AWS, Azure and GCP, the rule, the attack fixture, the hard-benign fixture, the sidecar cases, the benign-corpus slices and the budget are all authored by the same agent from the same reading of vendor documentation. A schema misconception is replicated identically in every artifact and every gate passes.

**Evidence (verified).**
- `detections/cloud/fixtures/`: 17 folders, 50 attack and 60 benign records in total, all hand-written; five attack files hold exactly one record. The validator still prints "All 32 external-cloud detection(s) fired on their recorded attack fixtures".
- Sidecar `source` fields: 1,276 of 1,380 cases begin with "synthetic"; 104 carry any non-synthetic source, all of them Linux or Kubernetes lab records or source-code citations. Zero cloud cases are recorded; the one cloud positive marked "recorded shape" is a byte-for-byte copy of a record in the repo's own synthetic fixture.
- 9 of 16 benign slice specs cite the repo's own TRR fixtures as provenance.
- No workflow runs a cloud atomic. `--show-fixture` prints the committed JSON. The live path of `emulate_entra.sh` creates and deletes a throwaway app and exports nothing, so even a human running it in a tenant has no scripted way to turn the real record into a fixture.
- Budgets are self-derived by design: `max_hits` is "the most hits the rule raised over the committed seed and ten reseeds".
- The word "recorded" is the vocabulary of the agent's instructions and tooling: `SKILL.md` ("recorded log fixtures", "the recorded attack"), `build-and-prove.md:388` ("Fixtures are schema-faithful recorded logs"), `validate_cloud_detections.py`, the cloud workflow header, `README.md:20`, `AGENTS.md:88`. Meanwhile `research/trr9015/aws/README.md:284` and `trr9021/aws/README.md:331` say "documentation-derived, not captured", and `SKILL.md:87` records two past cases that "pass a hand-made fixture and fail against real logs".
- `RULE_DEFECTS.md` K64 and K66 record cloud rules whose field casing is "unverified against primary docs"; 15 entries carry the ledger's required "unverified" marker. All 57 entries cite evidence kinds produced inside this pipeline; none cites an external reporter or a deployment.

**What the repo already says.** The inner docs disclose the constraint (no free live cloud target; fixtures grounded on schema docs; emulations not run in CI) and `COVERAGE.md` splits Proven by platform, so a reader can tell which rules are cloud. What a reader cannot tell is that "recorded" means hand-written, because the top-level files and the agent's instructions use the word for both.

**Why it matters.** A green cloud rule matches the agent's model of the log. The failure class is not hypothetical: the skill's gotcha list and K64/K66 are instances, all found by reading, none by a gate.

### 2. "Proven" is computed from repository text, and one word covers two evidence standards (medium)

**Evidence (verified).**
- `research/tools/coverage_report.py` has two code paths. Kubernetes: the TRR's emulation cell is exactly "built" and the rule appears in a `PROCEDURES` dict imported from the validator source (a static dict, not a run result). Everything else, Linux included: `cell.startswith("built")` parsed by regex from the README table (`:178-179`) and the rule's filename as a substring of the concatenated validator source (`:156`, `:164-168`), plus a sufficiency pass. No CI result is read anywhere, and the coverage-report job has no dependency on any validator job.
- Six cloud rules have no sidecar and pass `check_sufficiency.py` with rows like `0c+1f 1/3 PASS`. The `f` is a hard-benign-fixture record graded as a single-flip negative, a documented fallback (R2 docstring, `detections/README.md:174-176`, `SKILL.md:42-43`), so these rules are not ungated; but `AGENTS.md` item 3 omits the fallback, and one of the six (`gcp_workload_identity_federation_sa_binding.yml`) has no positive evidence anywhere except a two-record fixture that fails under compact JSON. Their procedures count as Proven (eight procedures).
- Sidecar provenance is free text that no tool reads: prefixes include "synthetic", "real", "recorded", "recorded via source", "real lab record", "synthetic from recorded mechanism", "recorded shape".

**What the repo already says.** `COVERAGE.md` "How the statuses are set" and "Limits of this report" state that Linux and cloud use a rule-level test and name the 12 unmapped rules. Every validator is a required status check in the live ruleset, so MANIFEST membership is an indirect proxy for "passed its validator on the PR head". CI passes `--require-audit`, so a missing auditd fails the Linux job rather than skipping. `check_schedule_freshness.py` surfaces a red weekly run within days. The path-skip hazard is documented as a residual gap.

**Why it matters.** The headline "66 of 157 proven" cannot distinguish evidence tiers, and the repo's own `README.md:53-54` ("its own emulation runs in CI") is false for the 25 cloud procedures. The fix is small: provenance as an enum, tiers in the report, and the README sentence.

### 3. The oracle's semantics are accidental, and the cloud rules are written to the oracle (high for cloud, documented for Kubernetes)

**Evidence (verified by probe through the repo's own evaluator).**
- `gcp_workload_identity_federation_sa_binding.yml`: 1 hit on its attack fixture with default `json.dumps`, 0 with `separators=(',', ':')`. `gcp_workforce_principalset_privileged_binding.yml`: the same, and all 12 of its sidecar positives flip too. These are the only two rules that hard-code the serialiser's spacing; seven others list both forms or use `\s*`. Both GCP rules disclose their field model in their description.
- `verb: 'Create'` on `verb=create` misses (SQL `=`); `verb|contains: 'Create'` hits (`LIKE`); `user.groups: 'system:masters'` on a list field misses; `|contains: 'system:MASTERS'` hits. Re-running all 1,380 cases with `PRAGMA case_sensitive_like=ON` flips exactly one verdict, a positive in `k8s_admission_webhook_repointed_to_url.yml` whose comment relies on "Sigma's default case-insensitive matching".
- `sigma_eval.py:7-8` says the SQLite result is "the same answer any conforming backend would give". The null-safe meaning of `not` and the portable regex subset are specified and gated; case folding and list equality are specified nowhere.
- `check_sigma_regex.py` caps values at 1,000 characters and CI compiles them under RE2; it measures nothing about anchoring or Lucene's determinisation budget, which rule comments reason about. 369 `|re` values; 126 exceed 500 characters, and 112 of those are in AWS rules (13 in Kubernetes, 0 in Linux). `aws_resource_policy_made_public.yml` has 57 selections, 144 atoms, 100 regexes and a 2,749-character condition.
- No processing pipeline exists for any cloud store. The stock Kusto backend renders the Entra device-code rule with its field names as string literals.

**What the repo already says.** For Kubernetes this is handled: `check_provider_mappings.py` runs compact and sorted serialisations for AKS and GKE as a gate (0 divergences), runs the exploded-array mode as a warning (19 of 40 rules diverge), and `PLATFORMS.md` marks each such rule with an `L` and says the EKS store "loses the `L` items". `pipelines/README.md` names the stores that keep JSON text (Splunk `_raw`, Elastic `event.original`, CloudWatch `@message`, KQL `dynamic`) and the ones that explode arrays, and says the loss is silent. The first draft's statement that no SIEM indexes a nested array as its JSON text was wrong; the correct statement is that stores which explode arrays have no such field.

**Why it matters.** For the cloud rules, "fires in CI" is a property of this harness. A consumer loading them into a store that explodes arrays gets silent non-detection. The gap is specific: extend the representation checks that exist for Kubernetes to the cloud rules, state the semantics, and stop writing grammars in regex where the provider already delivers a parsed object.

### 4. The negative evidence tests one mutant class, and the escape hatches are self-approved (medium)

**Near-miss is not mutation testing.** `rule_cases.py` accepts a near-miss when flipping the declared atom fires the rule (and rejects trivial and wrong-branch flips). That kills the "delete this item" mutant only. It cannot find a missing field, an over-broad `contains` or a wrong field name, because positive and near-miss carry the same wrong name. Median items exercised: cloud 50%, Kubernetes 67%, Linux 67%. R5 warns only below half the platform median (cloud 25%), so `aws_github_oidc_role_trust_ref_wildcard` at 4 of 13 passes silently. The exercised set is ratcheted against loss but nothing pushes it up. The ledger's own evidence kinds show K14, K16, K33 and C15 were found by source reading and probes, not by the gate.

**The Linux no-op control cannot fail** (added by the challenge pass, verified). `controls/noop.c` makes no syscall that `audit/atomic.rules` audits, so no event from its tree can ever reach a rule. `validate_detections.py:714-721` grades vacuity only for mutants with an `expected` list and passes `None` for the no-op, so 15 "held" rows print on every run. The README says a control whose tree made no audited syscall "is vacuous ... and fails the run". After removing those rows, 7 of 15 Linux rules have no live negative control at all.

**The exhaustive search stops at 12 atoms** (`check_sufficiency.py:874`); 16 rules exceed it. The first draft said the gate weakens there; that was wrong. `_lone_atoms()` feeds only the advisory hint text, not pass or fail, and the ledger's "Checks to add" documents the cap. What stands: no gate repeats that search above 12 atoms, and nothing caps rule size.

**Allowlists.** The first draft claimed `copyfail_af_alg_authencesn.yml` is silenced by renaming the binary. That was refuted: its filter pairs `comm` with `exe: /usr/bin/kcapi-hasher`, a rename alone still fires, and CI runs no rename control on it. The accurate picture: six rules have comm-only allowlists that the rename control exercises (bpf_prog_load, afinet, afpacket, keyring, perf, setns); the control's documented purpose is to prove the filter is live, which it does; `setns_namespace_join.yml` (level high) documents the `prctl` rename evasion in its own text and L14 records the class; `afinet_raw_socket.yml` and `afpacket_raw_socket.yml` carry no such note. On Kubernetes, 17 of 42 rules have a `filter_*` block reading `user.username`, and 41 of 42 also hold a near-miss, so identity filters are not the only negative anywhere but Linux's `linux_static_pod_manifest_write.yml`, which R5 flags. Nothing in the gates classifies a filter by whether an attacker controls its field.

**Waivers.** 27 `CHOKEPOINT` entries over 25 rules (one stale and flagged at HEAD); they apply to pure-surface rules with no discriminating item, and each waived rule still holds 2 to 11 verified negatives. The digest pins the rule, not the approver; no entry carries an approver, PR or date; `git show 9192e04` adds three waivers in the same commit as the rules they excuse. Across all 58 merged PRs there are seven reviews, all COMMENTED. The inner docs say single-maintainer sign-off is the intended path.

**Why it matters.** The gates are required and do fail (R0 to R4), so "gates that do not gate" was unfair. The fair statement is that the negative evidence is one mutant class deep, the Linux layer's universal control is vacuous, and the escape hatches have no independent approver.

### 5. False-positive measurement is a regression ratchet on self-written data, and the real signal is not consumed (medium)

**Evidence (verified).**
- All 16 slices are synthetic, authored by the same account that wrote the rules, with `adjacent_to` naming the rules they sit beside and which filter suppresses which template. PR #49 added `uid`, `euid` and `auid` to all 102 auditd templates in the same commit that made the rules' allowlists require euid 0; the template beside the keyring rule received the value the new filter needs.
- 43 budgets, all enforce, budget >= hits by construction, six at exactly their hits; `max_rate_per_10k` exists and is used by none. 11 level-high rules have a non-zero budget; `linux_k8s_sa_token_read` (high) has 266, and its own defect entry L16 says it fires about once a minute per workload.
- 50 zero-hit rules; about half (25 by my parse) are adjacent to no slice, so their zero is absence and is reported as `ok`.
- The live Linux capture: `keyring_add_key_burst.yml` hits 7 or 8, budget 0, `systemd-executor x6-7`, in every one of the 18 main-branch runs since 2026-10-16; `afpacket_raw_socket.yml` budget 0 fires on `arping` in all 18; `ptrace_traceme` on strace and ltrace in all 18 while the slice models strace as `PTRACE_SEIZE`. The ledger's "Live-capture hits not yet attributed" section was written from the run that contained the keyring row and omitted it; its afpacket entry says "a real fire would fail if the capture were a committed slice". The rule's `comm` list has `systemd` but not `systemd-executor`.
- The Linux capture expires after 30 days; the kind telemetry after about 90.

**What the repo already says.** Every entry point says hits are presence indicators, not rates, and that budgets are a ratchet; live hits are annotated as warnings and summarised on each run; a promotion path is described; the ratchet is non-required for a stated reason (with no bypass actors it would block legitimate case edits). A new recorded slice is meant to raise budgets in the same PR, which only the maintainer can merge.

**Why it matters.** The documented design is honest about what the numbers are not. What is missing is any mechanism that turns the one real signal into a case, a budget or a defect, and a check that `level: high` is consistent with a documented noise class. Three weeks of identical live warnings with no action is the measurement of that gap.

### 6. Prose and Python literals are the data model (medium)

**Evidence (verified).**
- `coverage_report.py` regex-parses the TRR README tables and `RULE_DEFECTS.md`'s Summary table and `Procedures` bullets; `score_benign.py` regex-parses the same Summary table. Both read only the table, so a defect with a heading and no row is invisible. 57 rows mirror 57 headings by hand.
- A technique touches up to ten hand-kept places (TRR, DDM JSON, `index.json`, the `research/README.md` table, a MANIFEST, waiver tables, the resource table in `k8s_policy_coverage.py`, acceptance tables in `check_provider_mappings.py`, and in `validate-apiserver-detections.yml` three path lists plus 18 emulate anchors mirrored as 18 aliases). A cloud technique touches about six. Many pairs do have agreement checks (index.json versus README procedures; budgets must name existing rules and listed defect IDs; waiver digests; resource table; acceptance re-proof; `--check` on five generated files). Two do not: the workflow path lists, and MANIFEST membership. A rule in a listed folder but absent from the MANIFEST compiles as "not manifest-gated" and the coverage report downgrades it to Claimed silently.
- The path-list fail-open is real but bounded: it affects the four path-filtered validators, every list also names the validator script (which a technique-adding PR must edit), the cheap gates have no path filter, and the weekly schedule runs everything. A technique missing from a list loses PR-time behavioural validation for up to seven days.
- `technique-selection.md`, which the skill says to read "first, every round", grew from 7,197 to 92,154 bytes between 2026-10-13 and 2026-11-04; its "Built" list has already drifted from `index.json`. The mandated up-front read is about 108 KB (AGENTS.md, SKILL.md, the ledger); with `UPSTREAM.md` and `build-and-prove.md` it is about 158 KB. `RULE_DEFECTS.md` went from 224 lines (after a cleanup in PR #48) to 2,699.
- `policy_coverage.json` (347 KB) changed in every Kubernetes PR; PRs are serial today, so conflicts are hypothetical until agents run in parallel.
- ATT&CK: `research/README.md` says v20 revoked `T1562.*`; the ATT&CK 20.1 bundle confirms `T1562.008` is revoked by `T1685.002` and the tactic list has no "Defense Evasion". TRR9038 (added 2026-11-04) is filed under `T1562.008` with tactic "Defense Evasion" and tag `attack.defense-evasion`; TRR9031 carries "Defense Evasion" while its rule tags `attack.stealth`. The `attacktag` validator is excluded from CI for a stated reason (it fetches over the network).
- `index.json` has no `status`, `prior_art` or `gaps` field; TRR status lives only in README prose and no tool reads it.

**Why it matters.** The design works while one agent works serially and one maintainer remembers the places. The ledger's growth rate and the parse-dependent tools are what break first; the fix is records plus rendered Markdown, a pattern the repo already uses for five files.

### 7. The proof-deciding code has no test suite, and its five validators share helpers by copy (medium)

**Evidence (verified).**
- No `test_*.py`, `*_test.py` or `conftest.py` anywhere. The proof-deciding set (`sigma_eval`, `sigma_explain`, `rule_cases`, `check_sufficiency`, `score_benign`, `check_null_safety`, five `validate_*.py`) is about 11,500 lines; all tracked Python is about 22,000. The first draft called all of it "proof engine", which over-counted.
- `check_null_safety.py --self-test` does exercise the core (constructed good and bad rules through `compile_rule`, `EventTable` and `run_case`) and runs in CI, though the job is not required. `sigma_explain.py`, the grader every near-miss verdict depends on, has a `_self_test` that no workflow runs. `check_sufficiency.py`, the most-edited gate file, has none.
- `_ts` and `load_ledger` are defined three times with different bodies; `write_json` and `dedup_by_audit_id` are byte-identical copies. The three ledger parsers disagree on `{"exit": true, "expect": 1}` (accepted by two, a hard problem for the apiserver one); the strict side fails closed, so this is a maintenance smell rather than a false-pass path.
- MANIFEST entries are 4-, 5-, 6- and 8-tuples; `check_sufficiency.py:614` finds the rule file by scanning for a `.yml` string and raises if there is not exactly one.
- The sufficiency ratchet compares head against the base branch's own copy of the script, so a defect present in both is invisible. No workflow reads a `validate_*.py --json` report; `rule_cases.py` has no JSON output.
- `detection-quality.yml:107-114` says "None of them is a required check in the main ruleset yet"; the live ruleset requires three of them. The prose is stale in the safe direction.

**What the repo already says.** The differential oracle in `rule_cases.py`, the planted Linux mutant against the validator's own success gate, and `--expect-miss` mean a gross evaluator regression would turn required checks red. A subtle false pass in the flip analysis or R2 would not, and nothing committed would show it.

### 8. The human loop is structurally thin, and the README overstates it (high)

**Evidence (verified through the GitHub API and the checkout).**
- Every commit on `main` is by the maintainer's account or by the agent (GitHub shows 75 commits: 61 under `vasquja`, 14 authored as "Claude"); no second human exists. The agent opens PRs under the maintainer's account, so GitHub forbids the approving review that `automerge.yml` rail 8 requires for any non-content change. The ruleset has `required_approving_review_count: 0` and no bypass actors.
- PR #60: +14,695 lines, 124 files, 8 TRRs, open 1 h 40 m, reviews COMMENTED only. PR #58: +17,441 lines, 50 minutes. PR #61: body said "Status: work in progress — please do not merge yet" and listed TRR9036 as "not yet in this PR" when merged, 17 h 45 m after its last commit; its merged rule `k8s_service_endpoints_hijacked.yml` lacked the `system:apiserver` filter and fired on the apiserver's endpoint reconciler (reproduced: 1 hit on the #61 rule, 0 on the #62 rule). Every required check was green.
- The only human-account review comments on #58 and #60 are replies to the bot's inline findings, "Confirmed and fixed in `f88da7b`", in the voice of the agent's PR body.
- 27 waivers carry no approver, PR or date. PR bodies carry a "Needs the maintainer" section (a prose decision sheet) and #62 asks the human to "re-approve by keeping that digest, or revert": approval by non-reversion.
- `README.md` says "a human-approved waiver", "a budget a human approves" and "passing work goes back to the human to merge"; the single-maintainer caveat is in `detections/benign/README.md:355-367` and `AGENTS.md`, not in the README.
- `automerge.yml` has merged one PR, its own live test (#47). It can never arm for a TRR PR because every TRR PR edits a validator. The label rail is enforced by a sentence in `AGENTS.md`, but its reach is bounded: content-only PRs only, where three gates are required and only the ratchet is not.
- `claude-code-review.yml` restores `.claude/` and `CLAUDE.md` from `origin/main` at run time ("PR head is untrusted"), but `CLAUDE.md` on main is the include `@AGENTS.md` and `AGENTS.md` is not restored, so the PR's own `AGENTS.md` still instructs the reviewer. Its output is COMMENTED and the rails ignore it, so a steered reviewer cannot approve or merge. Secrets are withheld from fork PRs. The action is pinned by floating tag.
- Issues are enabled (#55 is an open backlog); there is no issue template, nothing filed upstream, and no tuning surface beyond `falsepositives` text.

**What the repo already says.** The inner docs describe this exact structure and call the hand merge "the sign-off"; the second-identity fix is written down in `detections/benign/README.md:388-397` and `automerge.yml:185-189`. It is specified but not done.

**Why it matters.** The design promises a human gate on budgets, waivers and merges; with one identity it cannot operate, and the review identity blending means a reader cannot tell what a human did. The identity split is the precondition for every other process fix, and it costs hours.

### 9. The output is not yet consumable through the channel the repo names (medium)

The repo says "not for production" and names SigmaHQ, tired-labs and Atomic Red Team as its release channels. Judged against that channel:

- **Azure and GCP field vocabulary** (added by the challenge pass, verified). All 12 Azure and GCP rules declare SigmaHQ log sources (`azure/signinlogs`, `azure/auditlogs`, `azure/activitylogs`, `gcp/gcp.audit`) but match the provider's raw export fields (`protoPayload.methodName`, `protoPayload.serviceData.policyDelta.bindingDeltas`, `properties.*`, `category`). SigmaHQ's own rules under the same tags use `gcp.audit.method_name` and Sentinel column names. Nine tests in two files use `#{source_dir}` without declaring it, the defect class `upstream/atomic-red-team/FILING.md:41` records fixing once. Arguments drift from the MANIFEST (keyring `key_count` 100 versus 50; copyfail target paths). `UPSTREAM.md`'s readiness table still says 27 TRRs, 76 rules, 25 atomic directories; the generator prints 39, 91, 32.
- **Versioning.** No tags, no changelog; 17 of 91 rules carry `modified`; about half of the rules changed after their `date` without one, some rewritten four to six times.
- **Descriptions.** Median 30 lines, max 160, 36 over 40 lines; 31 mention harness internals (Lucene, `sigma_eval`, `RULE_DEFECTS`, three-valued logic). The skill tells the agent to explain mechanics "in the description" and the waiver digest excludes it, so it grows freely. Triage guidance does exist: all 91 `falsepositives` fields are substantive (median 528 characters; 82 name a baseline action) and about 14 descriptions give explicit pivots. No TRR has a triage, tuning or response section; the template has none.
- **Site tuning.** Five rules carry placeholder CIDRs inside detection logic with in-line comments on what to substitute, and the TRRs name the sources; there is no filter meta-rule or pipeline variable, and `PLATFORMS.md` states the managed-cluster false-positive rate is unmeasured because no rule filters `eks:*` or `aksService` principals.

### 10. The research layer: procedures, DDMs, prior art, and the Linux rules outside it (medium)

- **Procedure identity.** TRR9011 maps one rule to procedures A to D which the rule cannot distinguish (they differ in `ec2RoleDelivery` version or in an SSM anchor); TRR9036 A and B differ by a scope string the same regex matches. Twelve procedures are gaps or scope notes ("EKS Pod Identity (out of scope)", "Residual detection gaps", "Grading boundary"); they lower the headline Proven share rather than raise it, and distort only the "23 researched procedures have no detection" line. TRR9011 records other gaps as prose, so gap-as-procedure is an authoring choice that the repo's own definition forbids, enabled by `index.json` having no gaps slot.
- **DDMs.** 101 of 157 have three nodes; half of the DDM property keys restate the covering rule's fields and half are narrative. No tool relates a DDM property to a rule item; PNG-to-JSON drift is gated, rule-to-DDM drift is not (no drift was demonstrated in the TRRs compared). The per-procedure format is mandated by the tired-labs target, so the fix is a lint, not a format change.
- **Prior art.** TRR9036 cites an Elastic rule by a filename that never existed and says it keys on "the same" GUIDs as a "near-1:1 graded match"; the real rule lists six GUIDs against the repo's four and has no scope predicate. External links are not checked; `index.json` has no prior-art field; the only enforcement is the agent's own vet.
- **Eleven Linux rules sit outside the model** (added, verified). `research/README.md` says research comes first and the TRR drives the rule; 11 of 17 Linux rules (all seven under T1068, setns, memfd, ptrace, io_uring) have no TRR, no procedure ID, no DDM and no vetted prior art, and `COVERAGE.md` excludes them. ### 11. Safety and supply chain (medium)

**Evidence (verified; counts corrected by the challenge pass).**
- 17 cloud scripts are gated by `TRR90NN_LIVE`; two have an EXIT trap with a real undo; four are read-only in their live block; eleven tamper then restore in consecutive commands under `set -euo pipefail` with no trap, so a failure or Ctrl-C between the two leaves the change in place: Block Public Access off and a public bucket policy applied (`emulate_aws_public_exposure.sh`), the `_Default` logging sink disabled (`emulate_gcp_log_sink.sh`), an Owner assignment at subscription scope (`emulate_azure.sh`). The trapped and untrapped scripts were added in the same commit, so the pattern is known and unenforced. Every script requires the operator to name a throwaway target and never runs in CI; `AGENTS.md` says "emulations stop before harm" and nothing documents what a dead live run leaves behind.
- 20 Kubernetes scripts call `kubectl` and none checks the current context. Their deletes target their own `trr90NN`-named objects, so the blast radius is bounded, but the static-pod manifest write and the server-side-apply of webhook configurations are real writes against whatever context is current. In CI the context is always a freshly created kind cluster.
- All 46 `uses:` are floating tags; no `dependabot.yml`. The only third-party action is `anthropics/claude-code-action@v1`, in a read-only job that holds the OAuth secret. `sigma-cli` is installed unpinned in the required `sigma-lint` job and today resolves to pySigma 2.0.2 while the validators pin 1.5.1: a major version apart.

## How to design it better

The first version of this plan proposed a validator package extraction, a per-technique registry format, an Elasticsearch execution matrix, a per-SIEM release workflow and a second model. The realism judge rated those as sized for a team and in two cases technically mistaken (pySigma pipelines transform rules, not events, so parsing cannot move into a pipeline; CI cannot commit to `main` under the ruleset). This version keeps what fits one maintainer and one agent, and orders it by what unlocks what.

### Principles

1. **Split identities first.** Nothing that asks for a human approval line can work while the agent and the maintainer are one account.
2. **Every claim carries typed provenance, and the label follows the weakest link.** `captured-live`, `captured-lab`, `third-party-sample`, `reasoned-from-source`, `synthetic`. A rule's tier is the strongest provenance that fires it. Nothing synthetic is called recorded, anywhere, including in the agent's instructions.
3. **Get one record per log source that the agent did not write.** That is the only fix for the closed cloud loop, and it is cheaper than any new check.
4. **Test representation inside the oracle that exists.** Extend `check_provider_mappings.py` and `sigma_eval.py` rather than adding an engine: compact JSON, a multi-valued list model, and an RE2 regex function.
5. **Data generates prose.** Defects, waivers, budgets, candidates and required checks as records; Markdown rendered with the `--write/--check` pattern the repo already uses.
6. **Ratchet complexity and gates on new work; do not fail the existing corpus on day one.**
7. **Write for the stated channel.** Field vocabulary, `modified`, licence and the ART YAML are what SigmaHQ, tired-labs and Atomic Red Team will judge.

### The minimal set, in order

1. **Agent identity split.** The agent opens PRs from a machine account or GitHub App that cannot add labels. Add `.github/CODEOWNERS` for the non-content paths; turn on code-owner review and "require approval of the most recent push"; keep required approvals at 0. This is the setup `automerge.yml:184-189` already prescribes. Cost: maintainer about 3 hours, agent about 2 hours.
2. **Truth in labelling.** A provenance enum on sidecar `source`, fixture records and slice `fidelity`, enforced by lint; coverage tiers (`proven-live`, `proven-recorded`, `proven-synthetic`, `claimed`) in `coverage_report.py` and the chart; fix "recorded" in `README.md:20`, `AGENTS.md:88`, `SKILL.md`, `build-and-prove.md:388`, the validator and the workflow header; fail R3 on a missing sidecar. Cost: agent 1 day, maintainer 1 hour.
3. **One round of real cloud telemetry.** Add a shared `atomics/lib/live.sh` with an undo stack and `trap run_undo EXIT INT TERM` to the eleven tamper-restore scripts, a lint that fails any `_LIVE` script without it, and a capture mode that exports the provider's records. Run the 17 scripts once in sandbox accounts, sanitise, and commit the firing records as recorded positives and the pre-emulation window as the first recorded benign slice in shadow mode. Cost: maintainer half a day plus sandbox accounts, agent 2 days.
4. **Representation variants in the existing oracle.** A compact-JSON flatten over every sidecar positive and cloud fixture (fails one rule today); an RE2 `regexp` function in `EventTable` as the stand-in for Go and KQL; a `json_each` multi-valued list mode as a third `check_provider_mappings.py` provider, extended to the cloud rules. Gate as a ratchet (no new divergence) and record the 19 existing exploded divergences as accepted losses. Write `detections/SEMANTICS.md` stating case folding per modifier, list handling, null handling and regex dialect, with the probes above as golden tests; delete the "same answer any conforming backend would give" sentence from `sigma_eval.py`. Cost: agent 3 days, maintainer 2 hours.
5. **A known-bad set and tests as a required check.** Fifteen to twenty deliberately wrong rules, fixtures and cases that each gate must reject, run by pytest in `detection-quality`; wire `sigma_explain.py`'s existing self-test; add a `validator_common.py` for the five duplicated helpers and leave the validators' structure alone until the tests exist. Fix the Linux no-op control: grade vacuity for every control, and replace the no-op with a per-rule near-miss binary where one can be written. Cost: agent 2 days, maintainer 1 hour.
6. **Defects, waivers, budgets and required checks as data.** `RULE_DEFECTS.md` rendered from `defects.json` so `coverage_report.py` and `score_benign.py` stop parsing prose; waivers keep their content digest and gain `approved_by`, `pr` and `date`, and a rule PR may not add its own waiver (waivers land in a data-only PR under CODEOWNERS); budgets gain `class`, `defect`, `expires`, and a check that a `level: high` rule with a non-zero budget cites an open defect; `required-checks.json` compared with the live ruleset in CI (it would already catch the stale comment in `detection-quality.yml:107-114`). Cost: agent 2 days, maintainer 1 hour.
7. **Safety, freshness, channel hygiene.** Kube-context guard in the 20 kubectl scripts (refuse unless the context matches `^kind-` or an exported lab context); SHA-pin actions plus `dependabot.yml`; pin `sigma-cli` to match pySigma 1.5.1; a derived ATT&CK index (id, name, tactics, revoked-by, a few hundred KB, with the bundle's URL and sha256) and a check that every external ID, tactic and tag matches it; retag TRR9038 to `T1685.002` and `attack.defense-impairment` and fix TRR9031's tactic row; add a root `LICENSE` and a `license:` field per rule; an issue template. Cost: agent 1 day, maintainer 1 hour.
8. **Gate wiring.** Make `null-safety` required now; make `sufficiency-ratchet` required with a human-applied override label the job reads (only safe after step 1); drop the cloud workflow's path filter (the validator runs in one second); derive the Kubernetes and apiserver `changes` lists from each MANIFEST at runtime so the copies cannot drift; add a MANIFEST-membership check so a rule in a listed folder but absent from the MANIFEST fails rather than compiling as "not manifest-gated". Cost: agent 1 day, maintainer 30 minutes.

### After the minimal set

- **Close the live-capture loop.** A sanitiser for the runner and kind captures (hostnames, uids, temp paths to stable placeholders), committed weekly as recorded slices; `chokepoint_events` reported beside `hits` so a zero by absence reads `untested`; a grace-period gate that fails a budget-0 rule firing on the live capture on N consecutive runs unless a budget or defect lands.
- **Rules for the channel.** Processing pipelines for the cloud stores per target SIEM (CloudTrail, Entra and Azure Activity, GCP audit); a recorded decision on Kubernetes field names versus SigmaHQ's flat vocabulary, with a native-to-SigmaHQ pipeline if the repo keeps its own; fix the GCP path in `UPSTREAM.md`; regenerate its readiness table from the generator; a description template and lint (what, why, first pivot, what benign looks like; mechanics in `<stem>.notes.md`) and change the skill sentence that puts mechanics in the description; `modified` enforced by lint; an "Operate" section in the TRR template (triage pivots, baseline derivation for each placeholder, tuning keys, response order); site tuning as Sigma filter meta-rules per documented benign class; a lint over the ART YAML (declared inputs, executor present, arguments agree with the MANIFEST).
- **Complexity as a ratchet.** Atom count, regex length and exercised ratio recorded per rule and only allowed to improve; a type-aware lint that forbids regex only over fields the record carries as a list or object (CloudTrail delivers several policy documents as strings, where regex is the only Sigma-expressible test).
- **Research records.** `prior_art` (source, id, url, retrieved, sha256, excerpt) and `gaps` in `index.json`; a link check on References; a lint that every property on a DDM's shaded node names a field the covering rule matches; procedure identity as (entry primitive, logged signature) with a lint that two procedures covered by the same selection branch name the distinguishing field or merge; TRRs for the eleven Linux rules, or an explicit "legacy" tier that the README states; `status` flipped only by the review step.
- **Independence.** A blind case-writing step by a same-model subagent that sees only the TRR's procedure table and the vendor's field documentation, never the rule; a logged record of review findings the author rejected.
- **Release, later.** Only after the cloud pipelines and the field-name decision exist: render per-SIEM artifacts on a tag with a changelog from `modified` and defect transitions, and ship the per-rule trust manifest (`RULES.json`) joining defects, budgets, portability and provenance tier.

## Method and limits

Ten reviewer agents each took one dimension with read-only access to the checkout, a venv with the repo's pinned pySigma, and the GitHub API; they returned 65 findings and 50 strengths. The claims this document relies on were reproduced by hand. A second workflow of 29 agents then challenged the draft: for each of the eleven flaw sections a hostile fact-checker re-derived every number and citation and a fairness judge searched the repo for mitigations and candid disclosures; one architect judged the redesign against the actual pySigma backends, the ruleset and the workflows; one critic looked for missed dimensions, and each of its five additions was fact-checked by a further agent. The fact-checkers returned "partially confirmed" on every section: the structural claims held, one example was refuted (the copyfail allowlist), and about thirty numbers, line references and causal statements were corrected and are corrected here. The fairness judges lowered six sections from high to medium on the ground that the limitation is documented candidly in the inner docs; this version records both the flaw and the disclosure.

Two things were not verified. The Elastic rule's exclusion of an AKS false positive (flaw 10) comes from the research reviewer's fetch, which the second-round judge could not repeat (the repository returned 403 from this session); the six-GUID count and the absent scope predicate were repeated. Whether SigmaHQ's own validator pack would fail the rules on dates or titles was observed by the rule-quality reviewer and not re-run.

The reviewers were language models reading the repository, which is the limitation this review attributes to the project. They were instructed to cite file and line or command output for every claim and to say what they could not verify; the strengths section and the "what the repo already says" paragraphs exist because fairness to the repository was part of both briefs.
